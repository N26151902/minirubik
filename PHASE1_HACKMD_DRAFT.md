# CA2026 HW1 Phase 1 — Memory-Bounded Optimal Mini-Rubik Solver on RV32I

## Stage 1 — Baseline characterization

The fixed-corner 2x2x2 cube has 7! * 3^6 = 3,674,160 reachable states. The move set is generated by R, B, and D, with nine HTM moves: R, R2, R', B, B2, B', D, D2, D'. Exhaustive BFS establishes an HTM diameter of 11. The orientation invariant is the corner-twist sum modulo three; it is not a permutation-parity constraint.

The original full-state BFS approach is an excellent correctness oracle but does not fit the target memory budget because its table scales with the complete state space.

### Measured simulator characteristics

Same-process host-memory measurements:
- 32 KiB guest allocation: 124 KiB host-HWM increase = 3.875 host B / guest B.
- 64 KiB guest allocation: 196 KiB host-HWM increase = 3.0625 host B / guest B.

Ten-million-loop throughput measurements:
- RV32_ISS: 20,000,004 retired instructions in 0.582 s, about 34.36 M instr/s, CPI 1.
- RV32_5S: 20,000,004 retired instructions in 73.201 s, about 0.2732 M instr/s, 40,000,008 cycles, CPI 2.

These measurements make both memory and target instruction count first-class design constraints.

## Stage 2 — Target representation and algorithm

The final solver uses iterative IDA* with an explicit stack, so it needs neither recursion nor a heap. Optimality follows from iterative deepening with an admissible heuristic: the first solution found at the current bound has minimum HTM depth.

The state is split into permutation and orientation ranks. Transition tables update those ranks directly. The heuristic is the maximum of five admissible lower bounds: permutation distance, orientation distance, one 4-cubie pattern database, and two 3-cubie pattern databases. Taking the maximum preserves admissibility. The tables are generated offline and linked read-only; the target executes the search. No complete 3,674,160-entry distance table is linked.

The final solver has .rodata = 120,649 B, .data = 0 B, and .bss = 4,128 B. Thus the exact rubric sum .data+.bss+.rodata is 124,777 B, below 128 KiB. Including the small-data sections in the conservative audit gives 124,788 B, also below the limit.

## Stage 3 — C optimization and verification

The final C design was used as the algorithmic reference before translation. Host verification established heuristic admissibility over all 3,674,160 reachable states with zero violations, valid PDB population/solved/max checks, and zero optimal-distance mismatches against the exact BFS oracle.

The target validation harness applies every returned move and independently verifies the final solved state. Its three tests are: solved state (0 moves), a short scramble (1 move), and required vector 21345671111111 (11 moves). The same validation ELF passes on RV32_ISS and RV32_5S with final a0=0.

## Stage 4 — Handwritten RV32I

The submitted path is:

solver_solve_rv32 -> valid_rv32 -> solve_v5_rv32 -> rank/pattern extraction -> heuristic_v5_rv32 -> search_v5_rv32_handwritten_final

The hot path uses no RV32M instructions and no compiler multiplication/division/remainder helpers. Products by constants are implemented using shifts/adds or avoided by hoisting table-row addresses.

### Iterative refinement

| Version | Change | .text | Retired instructions |
|---|---|---:|---:|
| CP1 | explicit-stack search, loop-based pattern updates | 3,080 B | 21,950,326 |
| CP2 | unrolled 3-/4-cubie pattern updates | 3,244 B | 17,738,811 |
| CP3 | hoisted transition-row bases | 3,244 B | 17,137,243 |

CP1 to CP3 reduces retired instructions by 21.93%.

### GCC -O2 reference

The final C algorithm was compiled with GCC 14.2.0 using -O2 -march=rv32i -mabi=ilp32.

| Build | .text | Retired instructions |
|---|---:|---:|
| GCC -O2 final C | 3,712 B | 20,568,913 |
| Handwritten final | 3,244 B | 17,137,243 |

The handwritten implementation is 12.61% smaller in linked .text and retires 16.68% fewer instructions on the report vector.

### 50-million-instruction gate

Required vector 21345671111111 has optimal length 11 and retires 17,137,243 instructions. The known worst measured distance-11 state retires 48,276,932 instructions, leaving a margin of 1,723,068. A final reliable sweep used ecall 93. All 2,644 distance-11 states passed with zero failures. The maximum was 48,276,943 retired instructions on state 14325670000000, leaving a margin of 1,723,057 instructions.

## LED visualization

The visualization is also handwritten RV32I. led_renderer_rv32_fast.S uses the Ripes symbols LED_MATRIX_0_BASE, LED_MATRIX_0_WIDTH, and LED_MATRIX_0_HEIGHT, with a 35x25 matrix and row-major 32-bit RGB pixels.

The selected GUI build is led_asm_build_fast/fixed_5move_d2000.elf. It receives the actual move sequence produced by the solver and redraws the cube after solver moves; it is not a prerecorded animation. The five-move demonstration finishes with a0=0.

The renderer is excluded from the performance-gate build. Its fast facelet writer computes 35*y as (y<<5)+(y<<1)+y and writes a 4x3 facelet directly.

## Pipeline walkthrough notes

For the Ripes walkthrough, use RV32_5S and step through a short query rather than the distance-11 benchmark. Explain each selected instruction at two levels: architectural behavior and pipeline behavior.

Useful examples:
- lw: address is formed in EX, memory is read in MEM, and RegWrite commits the loaded word in WB.
- sw: address is formed in EX and memory is updated in MEM; there is no register writeback.
- add/addi: ALU result is produced in EX and written in WB.
- conditional branch: operands are compared and the next PC is selected through the branch path; no GPR writeback occurs.
- jal/jalr: control flow changes while the return address is written when rd is nonzero.

During the GUI demonstration, point out register-file write enable/writeback selection, ALU-input selection, memory write enable for sw, and changing PC/pipeline-stage occupancy. The LED MMIO sw is a clear example that a store reaches MEM and updates an external device.

## Ripes GUI pipeline and MMIO walkthrough evidence

A manual RV32_5S GUI walkthrough was performed with led_asm_build_fast/fixed_5move_d2000.elf.

At cycle 4, five different instructions simultaneously occupied WB, MEM, EX, ID, and IF, directly demonstrating pipeline overlap. At cycle 5, the first instruction retired and its destination register changed, confirming the distinction between pipeline occupancy and retirement.

The first LED framebuffer store at address 0x11154 is:

    sw x31, 0(x7)

It was followed cycle-by-cycle through ID, EX, and MEM. The immediately preceding address construction creates a RAW dependency:

    lui x28, 0xf0000
    add x7, x7, x28
    sw  x31, 0(x7)

The register file still displayed the old x7 value while the dependent store advanced, consistent with the processor's hazard/forwarding handling. In EX the store forms the effective address; in MEM it performs the memory-mapped I/O write.

For the captured first pixel, x31/t6 = 0x000000ff. Ripes exports LED_MATRIX_0_BASE = 0xf0000000, WIDTH = 0x23 (35), and HEIGHT = 0x19 (25). Immediately after the store crossed the MEM-stage clock edge, one blue LED appeared. This directly connects an RV32I store, the MEM stage, the MMIO framebuffer, and the visible device state.

After removing the breakpoint and running the renderer, the complete six-face cube net was displayed on the 35x25 LED Matrix with six colors. This confirms the visual pipeline execution of the handwritten renderer on RV32_5S.

## Arbitrary assembly-time input

The target accepts the required canonical 14-character state through inline_state_rv32.S. The first seven characters are permutation digits 1..7 and the next seven are orientation digits 1..3; the handwritten parser converts both groups to the zero-based representation used by the solver. build_inline_target.sh STATE supplies the string at assembly time, so a grader can rebuild the same program for an unseen state.

This path was tested with 21345671111111 (17,137,363 retired instructions), distance-10 state 25416373331111 (2,704,769), and worst measured distance-11 state 14325671111111 (48,277,063). All exit with real ecall-93 code 0 on RV32_ISS. A one-move inline state also passes on RV32_5S in 3,737 retired instructions / 4,902 cycles.

The LED build uses the same inline-state object through build_inline_led.sh STATE DELAY.
